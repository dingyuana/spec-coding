# 第9章：让规格“活”起来——Agent 自动维护活文档

> **写给已经拥有完整系统的你**：上一章，你的注册 API 正式上线了——24 个测试全绿，Flask 服务器能响应 curl 请求，密码被 bcrypt 哈希后存入 SQLite。但让我们诚实面对一个问题：三个月后，你（或你的队友）还能一眼看出“这个系统满足了多少需求”吗？
>
> Spec.md 躺在 `docs/` 文件夹里，测试散落在两个文件里，需求、测试、代码之间的追溯链是隐形的。如果现在有人问你：“`EMAIL_ALREADY_REGISTERED` 这个错误码在哪些测试里被验证了？”你能在 30 秒内回答吗？
>
> 本章，我们要做一件把 Agent 驱动开发推向极致的事：**让 Agent 自动生成并持续维护需求追溯矩阵和测试报告。** 从今天起，你不用再手动更新任何文档——Agent 会在每次测试运行后，自动把 Spec.md 和测试结果“缝合”成一份活的需求验收报告。

---

## 9.1 问题的根源：文档是“死”的，Agent 能让它“活”

还记得我们第 3 章认真写的那份 Spec.md 吗？它定义了 5 种错误码、10 条边界条件、5 条业务规则。现在请回答一个灵魂拷问：

> **你能不能在 30 秒内告诉我，这 24 个测试中，哪些是验证“邮箱格式”的？哪些是验证“密码强度”的？如果 3 个测试失败了，它们对应 Spec.md 里的哪一条？**

目前的答案很可能是：**不能。** 因为测试函数虽然名字清晰，但它们是“平铺”在两个文件里的，没有按需求维度组织。你只能在脑子里做映射，但脑子是会忘的。

SDD 的终极形态，是让 Spec.md **“活”** 在测试报告里——每次运行测试，都能看到“需求 A → 测试 1、2、3 → 全部通过”这样的可追溯链路。而这份链路，应该由 Agent 自动维护。

---

## 9.2 对 Agent 下达“活文档”指令

在 Task.md 第五阶段，还有两条未完成的子任务：

```markdown
- [ ] 生成需求追溯矩阵和测试报告
- [ ] 生成 HTML 测试报告
```

我们对 Agent 说：

> **“Agent，请执行以下任务：**
>
> **1. 读取 `docs/Spec.md`，提取所有规格条目（功能描述中的每一条约束、每个错误码、每个边界条件、每条业务规则）。**
>
> **2. 读取 `test_register.py` 和 `test_api.py`，提取每个测试函数的名称、docstring 和 pytest 标记。**
>
> **3. 建立双向映射，生成 `traceability.md`，格式为表格：规格条目 | 对应标记 | 测试函数 | 类型 | 状态。**
>
> **4. 运行 `pytest test_register.py test_api.py -v --html=report.html --self-contained-html`，生成 HTML 测试报告。**
>
> **5. 确认 24 个测试全绿后，将当前日期和全绿状态写入 `traceability.md` 的更新记录。”**

## 9.3 Agent 的输出：traceability.md

Agent 收到指令后，会按以下步骤自动执行：

1. 解析 Spec.md 的结构化内容（利用我们写好的 YAML 头部和表格）
2. 扫描两个测试文件，提取函数名、docstring、`@pytest.mark` 装饰器
3. 交叉匹配：每个规格条目 → 对应的 pytest 标记 → 具体的测试函数
4. 运行 pytest 获取最新状态
5. 写入 `traceability.md`

```markdown

> 每次测试运行后自动更新状态。
```

## 9.5 Agent 的输出：HTML 测试报告

同时，Agent 运行了以下命令：

```bash
pytest test_register.py test_api.py -v --html=report.html --self-contained-html
```

生成的 `report.html` 是一个独立的 HTML 文件，用浏览器打开后会看到一个漂亮的报告页面，包含：

- **Summary**：24 passed, 0 failed, 0 warnings
- **Environment**：Python 版本、平台、依赖包列表
- **Results**：每个测试的名称、标记、耗时、通过状态
- **过滤器**：可以按通过/失败/标记筛选

这份报告可以发给队友、老师、甚至产品经理。它不是冰冷的终端输出，而是一份**活的需求验收证明**——任何人打开它，都能看懂“目前系统哪些功能是正常的”。

## 9.6 活文档的哲学：一条指令，三份产出

回顾本章，我们只对 Agent 说了一句话，但它自动完成了：

| 产出 | 文件 | 用途 | 维护方式 |
|------|------|------|---------|
| 需求追溯矩阵 | `traceability.md` | 需求 → 测试的双向映射 | Agent 每次测试后自动更新 |
| HTML 测试报告 | `report.html` | 可视化验收证明 | 每次运行 `--html` 自动生成 |
| 覆盖率统计 | 包含在 `traceability.md` 中 | 快速发现未覆盖区域 | Agent 自动计算 |

这三份产出有一个共同特点：**它们不是“写”出来的，是“长”出来的。** 只要你维护好 Spec.md 和测试代码，Agent 就会自动把文档、报告、统计全部生成好。你永远不需要问“这个测试是测哪条需求的”——打开 `traceability.md`，一目了然。

## 9.7 当需求变更时：正循环演示

假设产品经理走过来对你说：“用户反馈 8 位密码太短了，改成最少 10 位吧。”

在 Agent 模式下，流程是这样的：

**第一步：你更新 Spec.md**

```markdown
### password
- **约束**:
  1. 长度: 10 ≤ len ≤ 64  # 从 8 改为 10
```

**第二步：你对 Agent 说**

> **“Spec.md 已更新：密码最小长度从 8 改为 10。请更新相关测试、代码和追溯矩阵。”**

**第三步：Agent 自动执行**

1. 修改 `test_register_invalid_password` 中的参数化数据：`"Abc1234"`（7 位）→ `"Abc1234567"`（9 位，刚好小于新的最小长度）
2. 修改 `test_register_valid_password_boundaries`：`"Abcdefg1"`（8 位）→ `"Abcdefgh1"`（9 位）？
   - 不对，密码刚好 10 位才是新边界。Agent 会改成 `"Abcdefgh12"`（10 位）
3. 修改 `register.py`：`PASSWORD_MIN_LENGTH = 10`
4. 运行全部测试 → 确认变红（旧测试与新常量不匹配）→ 重新调整 → 全部变绿
5. 更新 `traceability.md`：覆盖 11、15 条的测试描述自动更新
6. 生成新的 `report.html`

**整个过程不超过 3 分钟，而且你 100% 确定不会遗漏任何地方。**
