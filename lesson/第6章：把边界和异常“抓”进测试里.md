让我们回顾一下 Spec.md 的边界条件表：

- B8——✅ 已有 `test_register_email_normalization`
- B9/B10——✅ 已有两个 duplicate 测试

看起来好像都覆盖了？别急着下结论。**让 Agent 来审查。** 人类容易“看着觉得全了”，Agent 会逐格扫描 Spec.md 和测试文件，精确匹配。

## 6.3 Agent 的审查过程

Agent 收到指令后，会执行以下步骤（这是 Agent 的“思考日志”）：

### 步骤一：解析 Spec.md 边界条件表

Agent 从 Spec.md 中提取出 10 条边界条件，编号 B1–B10。

### 步骤二：扫描 test_register.py 中的所有测试

Agent 逐个测试函数读取，提取它们覆盖的边界编号：

| 测试函数 | 覆盖的边界 |
|---------|-----------|
| `test_register_email_exactly_255_chars` | B1 |
| `test_register_invalid_email[超过 255 字符]` | B2 |
| `test_register_valid_password_boundaries[8位]` | B3 |
| `test_register_valid_password_boundaries[64位]` | B4 |
| `test_register_invalid_password[7 位密码 < 8]` | B5 |
| `test_register_invalid_password[65 位密码 > 64]` | B6 |
| `test_register_valid_password_boundaries[空格]` | B7 |
| `test_register_email_normalization` | B8 |
| `test_register_duplicate_email` | B9 |
| `test_register_duplicate_email_case_insensitive` | B10 |

### 步骤三：比对结果

Agent 对照后发现：**10 条边界条件，全部已覆盖。** 但 Agent 不会就此停步——它会进一步检查是否有一些“隐含边界”没有被显式测试。

### 步骤四：发现隐含遗漏

Agent 在扫描 Spec.md 输入参数时注意到：

> **email 约束第 3 条**：“首尾空格自动去除”
> **email 约束第 4 条**：“统一转换为小写字母”

现有测试 `test_register_email_normalization` 测试了“首尾空格 + 大写”的组合场景（B8），但没有单独测试：
- **只有首尾空格、没有大写的情况**：`"  user@example.com  "` → `"user@example.com"`
- **只有大写、没有空格的情况**：`"USER@EXAMPLE.COM"` → `"user@example.com"`

此外，Agent 还发现 Spec.md 里有一条业务规则没有被测试直接验证：

> **业务规则第 5 条**：“依赖数据库 UNIQUE 约束保证邮箱唯一”

现有测试通过两次调用 `register` 来验证重复注册，但没有直接验证**数据库层面确实有 UNIQUE 约束**。如果有人在 `database.py` 中不小心删掉了 `UNIQUE`，测试依然能通过（因为 `UserRepository.exists()` 会先查一遍），但并发场景下就会出问题。

### 步骤五：Agent 的决定

Agent 决定补充 3 个测试：
1. 邮箱规范化——只有空格（分离测试）
2. 邮箱规范化——只有大写（分离测试）
3. 数据库 UNIQUE 约束验证

## 6.4 Agent 补全的测试代码

Agent 在 `test_register.py` 文件末尾追加以下测试：

```python
# ============================================================
# 第 6 章新增：Agent 审查后发现需要补全的边界测试
# ============================================================

@pytest.mark.normalization
def test_register_email_normalization_spaces_only():
    """补充测试 - Spec.md email 约束第 3 条
    
    验证：只包含首尾空格（无大写）的邮箱被正确规范化。
    """
    repo = UserRepository()
    
    result = register("  user@example.com  ", "SecurePass123", repo)
    
    assert result["email"] == "user@example.com"


@pytest.mark.normalization
def test_register_email_normalization_uppercase_only():
    """补充测试 - Spec.md email 约束第 4 条
    
    验证：只包含大写字母（无空格）的邮箱被正确转为小写。
    """
    repo = UserRepository()
    
    result = register("USER@EXAMPLE.COM", "SecurePass123", repo)
    
    assert result["email"] == "user@example.com"


@pytest.mark.duplicate_check
def test_register_database_unique_constraint():
    """补充测试 - Spec.md 业务规则第 5 条
    
    验证：数据库层面确实存在 UNIQUE 约束。
    通过直接操作数据库插入相同邮箱两次，确认会抛出 IntegrityError。
    """
    import sqlite3
    from database import get_connection
    
    repo = UserRepository()
    
    # 先正常注册一个用户
    register("unique_test@example.com", "SecurePass123", repo)
    
    # 尝试绕过 UserRepository，直接用 SQL 插入相同邮箱
    conn = get_connection()
    cursor = conn.cursor()
    
    with pytest.raises(sqlite3.IntegrityError, match="UNIQUE constraint failed"):
        cursor.execute(
            "INSERT INTO users (id, email, password_hash) VALUES (?, ?, ?)",
            ("fake-uuid", "unique_test@example.com", "fake_hash")
        )
        conn.commit()
    
    conn.close()
```

## 6.6 为什么让 Agent 审查测试覆盖？

你可能会说：“这些测试我自己也能想到，为什么要让 Agent 来审查？”

答案有三个：

### 1. 人类容易“视而不见”

当你盯着同一份测试文件看了 20 分钟，大脑会进入“熟悉模式”——它会自动补全你以为自己测了、但其实没测的场景。Agent 没有这个毛病。它是逐格扫描的，少一格就会报警。

### 2. 隐含需求会被遗漏

“数据库 UNIQUE 约束”这条，Spec.md 写在业务规则里，不是边界条件表里。人类审查时很容易只对着边界条件表打勾，而忽略业务规则里隐含的可测试条目。Agent 会扫描整个 Spec.md，不只看一个表格。

### 3. 分离测试比组合测试更有价值

原来 `test_register_email_normalization` 测试的是“空格 + 大写”的组合场景。如果这个测试失败了，你只能知道“规范化出了问题”，但不知道是空格处理出了问题，还是大小写处理出了问题。Agent 补了两个分离测试，让失败定位更精确。

## 6.8 边界测试的哲学：像敌人一样思考

这一章的核心技能，总结起来是一句话：

> **像攻击自己的代码一样审查测试覆盖。**

每次 Agent 完成测试生成后，你应该追问：

1. **每个约束都有正面和反面测试吗？**（长度 ≤ 255 → 测 255 和 256）
2. **每个“和”条件都被分离测试了吗？**（“去空格和转小写” → 测“仅空格”+“仅大写”+“组合”）
3. **每个业务规则都能被测试直接验证吗？**（“依赖 UNIQUE 约束” → 直接测 SQL 层）
4. **每个错误码都有触发它的测试吗？**（对着错误码表逐一打勾）

这不是“为了测试而测试”，而是**让 Spec.md 真正成为唯一真相来源**。如果一条规则没有测试，它就只是“建议”，不是“契约”。
