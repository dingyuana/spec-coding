# SDD+TDD 实战：大学新生报到系统 — 项目总览

> **场景带入 → 发现问题 → 方案迭代 → 原理拆解 → 效果对比 → 情绪升华**

---

## 一、一个真实的开学场景

九月初，计算机学院张辅导员打开手机，发现微信后台涌进来 120 条新生报到信息——张三身份证输错了、李四缺体检信息、王五重复提交了两次……

与此同时，教务处的王老师要在全校范围内统计"今天提交了多少、通过多少、哪个学院还没报到"，打开 Excel 花了两个小时。

最后，一个大一新生在校门口迷路，问遍了保安才找到宿舍楼。

**三个角色，三个痛点，一个系统。**

![](imgs/00/01-role-painpoint.svg)

## 二、最朴素的做法：三个独立系统

"学生端用微信小程序，管理端用网页，辅导员也用网页。"

这听起来合理。问题是：
- 学生端和管理端**各有一套登录**，密码策略不一致
- 辅导员看到的数据和管理员看到的**不一样**（辅导员只看本班）
- 校园导航要接入高德地图，每个端都要写一遍调用逻辑
- 最后发现——**审核、统计、日志**，三个端都各自实现了一遍

代码重复、逻辑分裂、维护成本翻倍。

## 三、换一种思路：SDD + TDD

**Spec-Driven Development（契约驱动）+ Test-Driven Development（测试驱动）** 的组合拳：

```
SPEC.md   → 三端共享的业务契约（"到底要实现什么"）
PLAN.md   → 迭代任务清单（"分几步做"）
AGENT.md  → 编码规范（"代码长什么样"）
specs/*.yaml → 模块级 OPEN-SPEC 契约（"每个模块的接口承诺"）
```

![](imgs/00/02-sdd-tdd-overview.svg)

**核心承诺：**
- 先写测试（RED）→ 再写代码（GREEN）
- 每个迭代 2-5 个文件，改坏立刻知道
- 105 个测试全绿才算完成

## 四、技术选型为什么是 FastAPI

| 选项 | 理由 |
|------|------|
| **FastAPI** | 异步、自动 OpenAPI 文档、Pydantic 验证 |
| **SQLite** | 教学简化，零配置 |
| **微信小程序** | 学生端，微信 code 登录 |
| **Vue 3 + Element Plus** | 辅导员/管理端 |
| **高德地图 + MCP** | 校园导航 |

FastAPI 的 `Depends` 依赖注入天然适合做"三端鉴权"——一个 JWT 中间件，三套角色分发。

## 五、项目架构一览

```
colldege_spec/
├── specs/          # OPEN-SPEC 模块契约（7 个 YAML）
├── src/
│   ├── core/       # config / database / auth / mcp
│   ├── models/     # SQLAlchemy 模型
│   ├── schemas/    # Pydantic 验证
│   ├── services/   # 业务逻辑
│   ├── routers/    # 路由（单文件 main.py 教学）
│   └── utils/      # errors / common
├── tests/          # 105 个测试（56 单元 + 49 集成）
└── frontend/       # miniapp + admin
```

## 六、三端登录的"一鱼多吃"

```
微信学生端   code → session_key → JWT(sub=openid, role=student)
Web 辅导员端 用户名密码 → SHA-256哈希验证 → JWT(sub=用户名, role=counselor)
Web 管理端   用户名密码 → SHA-256哈希验证 → JWT(sub=用户名, role=admin)
```

**同一套 JWT，三个 role**——后端路由根据 role 分发权限，辅导员只能看本班，管理员看全局。

## 七、写完一个项目的成就感

从零到 105 个测试全绿，12 个测试文件，50+ 源码文件。
这不是"能跑就行"——是"改了任何地方，测试立刻告诉你有没有坏"。

**代码有契约，测试有守卫。**
