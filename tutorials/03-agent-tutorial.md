# 把规范写成门禁——AGENT.md

---

## 一、先给你看段代码。不，是段罪证。

你在 Code Review 页面里往下翻，新来的 PR，改动不大，就几十行。

然后你看到了这个：

```javascript
const user = await db.query("select * from users where id = " + id);
ctx.body = { passwordHash: user.passwordHash };
```

两行代码，两个生产级漏洞。

**SQL 注入** —— `id` 是用户输入，直接拼进查询，一句 `' OR 1=1--` 就能把你的用户表全部 dump 出来。
**密码 Hash 泄露** —— 你把 `passwordHash` 原封不动怼进了响应体里，等于给所有注册用户的密文挂了张公示牌。

你深吸一口气，点了"Request Changes"。

然后你发现一个更绝望的事实：**这段代码 CI 是绿的。** ESLint 没报错。SonarQube 没报警。单元测试全过了。

![](imgs/03/01-three-layer-framework.svg)

**Linter 是语法门卫，不是架构门卫。**

再念一遍。**Linter 是语法门卫，不是架构门卫。**

ESLint 能管住你少了个分号、多了个空格、变量名不是 camelCase。**但它管不住 `select *`，管不住你把密码怼进响应里。** 它会告诉你"这里有个未使用的变量"——但不会告诉你"你正在把整个数据库的用户密码发给前端"。

这段代码在语法上是完美的。在架构上是灾难的。

---

## 二、Linter 管不了的东西，谁管？

你可能会说：那装个安全扫描器？加个 SonarQube 规则？

等你把"登录页面不能泄露用户是否存在"写成一条 SonarQube 规则给我看看。**你写不出来。** 这种语义级别的约束，静态分析工具根本理解不了。

那怎么办呢？

**把你的规范，写成一个文件。放在项目根目录。让人先读。让人对照着写代码。**

这个文件就是 **AGENT.md**。

打开 `user-login/AGENT.md`，核心就一张表——**禁止事项表**。

---

## 三、禁止事项表

这不是那种"建议你用更好的方式"的软绵绵废话。

这是门禁。每一条都是一道闸门。

| 禁止 | 原因 | 你干过没？ |
|------|------|-----------|
| 密码明文存储 | 必须 bcrypt，慢哈希，加盐 | 我赌你早期项目里至少有一个 `md5(password)` 还躺在那儿 |
| JWT 密钥硬编码 | 必须从 `.env` 读取，存到变量里 | 把 `secret: 'my-secret-key'` 写死在代码里的举个手 |
| catch 后吞异常 | 必须 `throw` 或转 `AppError` | `catch(e) {}` —— 全宇宙最常见的 Debug 消失术 |
| 登录泄露用户是否存在 | 防枚举攻击，错误消息必须完全一致 | "用户名不存在"和"密码错误"分开提示的，你就是在给黑客送字典 |
| 数据库查询不能拼接 SQL | 必须用参数化查询或 ORM | `"WHERE id = " + id` —— 经典款，贯穿三代程序员 |
| 敏感字段不能出现在响应体中 | 必须显式 `pick` 或 `omit` | 你肯定有过一次"卧槽我怎么把 passwordHash 也返回了" |

每一条 AGENT 的禁止项，最终都有一条测试在守卫：

```javascript
// AGENT 说：登录不能泄露用户是否存在
// tests/integration/auth.test.js
it('错误消息与密码错误完全一致（防枚举）', async () => {
  const [wrongPass, notFound] = await Promise.all([
    post('/api/auth/login', { username: 'admin', password: 'wrong' }),
    post('/api/auth/login', { username: 'ghost', password: 'x' }),
  ]);
  expect(wrongPass.body).toEqual(notFound.body);  // 完全一致，一个字都不能差
});
```

看见没？**AGENT 是一条人的约定，测试是一道代码的门禁。** 规范写进文件里，门禁写进测试里。人和机器一起守住一个标准。

## 四、AGENT 是什么？人肉可读的 Linter 配置

Linter 检查的是 **语法层**。

AGENT 检查的是 **认知层**。

Linter 告诉你："第 42 行多了个空格。"
AGENT 告诉你："第 42 行你把密码返回给了前端。"

Linter 的规则是机器执行的。AGENT 的规则是人读的、人执行的、**互相监督执行的**。

而且 AGENT 有一个铁律：

**只写禁止项和必须项，不写建议项。**

```
✅ 禁止：密码明文存储（这是一个停止命令。看到这条立刻打回 PR。）
❌ 建议：可以考虑用更安全的密码存储方式（没人会执行的模糊建议。等于没写。）
```

"建议"这个词，在 AGENT.md 里是违禁词。AGENT 不是一本"可以考虑"的手册——它是一座"你不能这么做"的门禁。

## 五、有 AGENT 和没 AGENT 的差距

| 场景 | 没 AGENT（丛林法则） | 有 AGENT（有法可依） |
|------|-------------------|-------------------|
| 新成员 | 看完代码猜规范，猜错了上线背锅 | 读完 AGENT 再写代码，一次说清所有红线 |
| 代码审查 | 凭 reviewer 当天的心情和耐心 | 对照 AGENT 逐条检查，reviewer 只是最后一道关 |
| 安全漏洞 | 上线后用户发现的，或者黑客发现的 | AGENT 提前拦截，测试二次确认 |
| 架构一致性 | 每个人写出八个不同的"规范风格" | 所有人都读同一份文件，写同一个风格 |
| 老员工离职 | 规范跟着人走，人一走就失传 | 规范写在文件里，谁来都能看 |

![](imgs/03/02-linter-vs-agent-comparison.svg)

**ESLint 管语法。AGENT 管架构。两条防线，少一条都是在裸奔。**

## 六、这还只是开始

规范写好了，红线画下了，门禁装上了。

但问题来了——你总不能让每个新来的同事自己去装依赖、配环境、建目录吧？

**你需要一个工程底座。** 一个放到哪都能跑的脚手架——`package.json` 写好依赖、`.env` 把密钥请进环境变量、`.gitignore` 把不该提交的东西拦在门外。

比如说，`.gitignore` 里忘了写 `node_modules/` —— 你知道那是什么后果吧？对，就是有人会把它 commit 上去，然后你的仓库变成 400MB 的怪物。

再比如说，`.env` 里没写 `JWT_SECRET` —— 你猜谁会把它直接硬编码在代码里？所有人。因为"反正我本地跑着没问题"。
